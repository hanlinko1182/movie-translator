## P1 operational acceptance

The one-slot policy is the conservative recommendation for the first Storyline paid implementation. It prevents a second unresolved M2 submission even if Redis redelivers, a lease expires or a process restarts. It is intentionally **not** a throughput target. One ambiguous request can stop all subsequent Storyline paid work indefinitely; users must see a truthful blocked state when a future UI exists, and operators need an escalation runbook. The slot remains held while the original checkpoint is `SUBMITTED` or `UNKNOWN`. Only a trusted definitive result tied to that checkpoint may move it to RESOLVED. No force button, manual row update, timer or “assume not charged” procedure is approved. This recommendation requires an explicit human product decision before live deployment.

## P2–P5 paid confirmation and budget policy

The future preparation step may calculate a bounded recipe and quote without spending. The confirmed POST must resolve a real server session, exact project/movie/Studio scope, task-create permission and a **separate spend permission** for that exact profile, recipe hash/bytes, Studio revision, source/script context, generation, quote version, amount and expiry. A server-issued single-use nonce/idempotency binding prevents replay; duplicate matching admission returns the existing task without another grant or call. Changing any binding requires a new quote and explicit confirmation. A local audit label, environment setting, M1 verification decision or user-authored proposal remains untrusted.

The [M2-01 structural limits](../lib/storyline/jobs/contracts.ts) cap request bytes at 1 MiB, response bytes at 512 KiB, tokens at 100,000 per direction, timeout at 120 seconds, proposal TTL at five minutes, estimated USD micros at 100,000,000 and reported USD micros at 1,000,000,000,000. These are **maximum representable bounds**, not approved operational values. No live provider/model, per-kind token budget, price or quote is selected here. A future fixed profile must supply lower or equal values plus provider/model, prompt/schema/validator/policy versions, and a cost-policy identity; its definition hash belongs in the immutable recipe.

For a quote, the trusted cost policy must use a pinned published/contracted price version and explicitly account for input/output ceilings and any known provider charges. Present it as **estimated maximum exposure under assumptions** unless a provider-enforced hard cap has been verified. A token ceiling or local timeout does not necessarily cap remote billing. Provider idempotency, hard cost caps, billing finality, remote cancellation and ambiguous-result retrieval are `UNVERIFIED` in M2-01. If a hard charge cap is required by the product and unavailable from the provider, keep live paid work disabled. Store missing usage/cost as `null`/UNKNOWN, never zero; record confirmed reported usage once per original submission, including failed validation, cancellation or stale publication.

## P3 privilege approval criteria

The former M1 role draft's `GRANT ... ON ALL TABLES IN SCHEMA public TO storyline_runtime` conflicted with the M2 read-only runtime boundary if applied after M2 tables. M2-02C replaced it with an explicit reviewed pre-M2 table list; disposable negative-login tests passed in **both** application orders. Before deployment, still inspect final privileges, inherited memberships and default grants on the actual target. The safe end state is distinct credentials for read, admission and checkpoint services, no owner credential in runtime, no ordinary direct M2 writes, no M1 issuer privilege in M2 roles, and only narrowly granted function execution after `SECURITY DEFINER` review. No such gateway is deployed by this review.

No review-only gateway SQL is added in M2-02B: an apparently executable function before the authenticated operator contract, grant payload and transition parity are approved would invite deployment of an unsafe placeholder. Gateway signatures and transaction invariants are specified in [the security review](STORYLINE_M2_SECURITY_GATE_REVIEW.md); executable role/function SQL belongs to a separately authorized disposable implementation and review.

## P6 acceptable UNKNOWN evidence and disposition

An investigation may use the original stored complete response, or a provider-authenticated lookup/support record whose provider request identifier and request identity can be bound to the exact checkpoint/generation. It must capture evidence source, acquisition time, digest, validation rule and authorized investigator in an append-only audit trail. A provider billing line may support a charge classification but is not necessarily proof of response content or finality. A caller-supplied receipt, screenshot, absence of a log, expired lease, timeout or unverified provider statement is insufficient. Where no definitive original-request evidence exists, leave the slot occupied and financial exposure UNKNOWN. No second provider request is an investigation step.

After a definitive original outcome is established, resolve only that submission. Preserve original normalized result/history and recheck authoritative current source/script before any candidate publication. If source became stale, preserve the result as historical and do not promote it to a current script. Human source verification, subtitle approval, script approval and duration support remain separate decisions. No manual investigation endpoint is authorized in this milestone.

## P7 observed compatibility decisions to resolve first

M2-02C resolved the observed review-only mismatch: LEASED → QUEUED retains generation and consumes one bounded dispatch attempt under the same unexpired grant; only an explicitly confirmed terminal retry advances generation. UNKNOWN with a pending cancellation reaches CANCELLED only after the original definitive result is stored and submission becomes RESOLVED. A grant is consumed at admission, never refreshed during redispatch, and expiry blocks checkpoint. No acknowledged checkpoint becomes automatically retryable. See [contract alignment](STORYLINE_M2_CONTRACT_ALIGNMENT.md).

The reviewed submission terminal name is `RESOLVED`, separate from task completion. Store amounts as integer USD micros; a quote is an estimate, while result usage is REPORTED, PARTIAL or UNKNOWN. Existing application migrations remain untouched.

## M2-03 fake-only acceptance boundary

**Recommendation: PASS for separately authorized, fake-only M2-03 contract implementation; BLOCKED for live paid activation.** The P7 review-only alignment is tested on disposable PostgreSQL. M2-03 may assemble the six-model draft only in a newly owned disposable database, use injected synthetic authority and fake providers, write task/outbox atomically, dispatch only `{taskId, generation}` to isolated Redis after commit, reconcile missing receipts and prove idempotent concurrent admission. Production entry points and Storyline paid workers must remain disabled by default; tests must fail if they attempt an external provider or application DATABASE_URL. This is not authorization to start M2-03 in M2-02C.

The following still block **live** use even after fake-only tests pass: P1 human approval, real P2 operator integration, P3 restricted roles and gateway acceptance, P4 fixed profile/model approvals, P5 price/cap decision, P6 audited investigation design, existing-database migration approval and a separately authorized paid activation. M2-03 cannot silently satisfy those gates by using a mock authority in tests.
