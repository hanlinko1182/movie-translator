# Storyline M2 paid admission security gate — review only

Status: **proposed architecture, no runtime authority**. This review does not install a database role, function, API, worker, model profile or provider transport. The M2 Prisma/SQL drafts remain outside live migrations; M1 receipt issuance and Storyline paid work remain disabled. Deployment is trusted-local today, without an authenticated spending operator or a public multi-user authorization model.

## Evidence and trust boundary

Reviewed the M1 final acceptance and restricted verification-role design, the M2 architecture/plan, the six-model M2 draft, M2-01 pure contracts, and disposable PostgreSQL tests. M2-02 established relational scope, a unique logical recipe, single-use grant shape, unique checkpoint and a PostgreSQL partial unique unresolved slot on `SUBMITTED`/`UNKNOWN`. Those tests used only synthetic records on a newly owned PostgreSQL cluster. They did **not** establish operator identity, actual provider billing, source currentness at a future network send, or safe production role grants.

The pure `inspectUntrustedStoryPaidProposal` returns `authorizesProviderSubmission: false`; `authorityAssurance` is `UNVERIFIED`. `parseStoryTaskProfile` checks structure but does not register or approve a model. M1's `createStorylineOperatorAuthority` is scoped to `VERIFY_SOURCE`/`REVOKE_VERIFICATION`; its audit grant is not a spending grant. Neither a local label nor a valid JSON/Prisma row can cross the M2 paid boundary.

**Privilege interaction found and corrected in the review-only draft:** the earlier M1 role script used `GRANT ... ON ALL TABLES IN SCHEMA public TO storyline_runtime`. Applied after M2, it would have granted broad M2 DML despite M2's `REVOKE ... FROM PUBLIC`. M2-02C replaced this with an explicit pre-M2 table list; disposable tests prove ordinary runtime lacks direct M2 DML in either application order. A future deployment must still inspect the actual target's role membership, default grants and object ownership; these drafts are not deployed credentials or gateways.

## Spending authority contract

Use a **separate, server-owned spending authority**. The future adapter must resolve a server session to a verified operator subject, then independently decide (a) whether that subject may view/prepare the exact project/movie, (b) whether they may create a Storyline task, and (c) whether they may spend for this exact one-call recipe and quoted exposure. These are different permissions; source-verification permission does not imply any of them. The selected movie ID must be checked against its project ID; project slug or a newest-movie fallback cannot substitute.

A confirmation decision binds: authenticated subject and authority provider/version; project ID, selected movie ID and Studio ID; task kind; canonical recipe hash **and exact server-stored bytes**; immutable source snapshot and optional script IDs/hashes; expected Studio revision; fixed profile definition hash and quote/cost-policy version; estimated exposure and any approved spend ceiling; a short expiry; one generation and one maximum provider submission; an explicit human acknowledgement time; and a scoped idempotency key. The browser may display and return a proposal identifier, but it cannot create or modify the trusted decision. Reauthenticate/re-authorize at confirmed POST; consume exactly once transactionally. Cloned/deserialized M1 operator tokens and user-supplied `authorityRef` values are not spending capabilities.

The server-side authority adapter is **deny by default** when no authenticated provider is installed, when session/permission/scope expires, when source/profile/price/revision changes, or when the confirmation was consumed. The real application currently has no such adapter. An environment flag or worker-running state cannot enable it. For M2-03, only an injected synthetic test authority is allowed; no production write entry point is installed or activated.

The M2-02 table stores `authorityRef` and structural binding, but it does not itself store a complete verified subject/action/decision proof or a scoped idempotency ledger. Before live promotion, decide whether to add immutable operator/provider/decision fields and a unique `(subject, project, movie, idempotencyKey)` binding or use a separately reviewed durable authority ledger. A hash or opaque label alone is insufficient, and no caller-supplied token may become trusted merely by insertion.

## Proposed PostgreSQL privilege matrix

| Principal | Allowed | Forbidden |
| --- | --- | --- |
| Migration/schema owner | Own M2 tables, enums, constraints and narrowly reviewed gateway functions during deployment | Application or worker connection; routine paid calls |
| Read-only runtime | Scoped safe task/status views and required source reads | Direct INSERT/UPDATE/DELETE/TRUNCATE on M2 paid tables; M1 receipt write; grant/checkpoint gateways |
| Trusted admission writer | Execute only an admission gateway after independent server authentication and explicit paid acknowledgement | Direct generic confirmation/task/dispatch writes; checkpoint/result/receipt issuance |
| Checkpoint worker | Execute only lease/checkpoint/outcome gateways for one fenced task generation | Create grants/tasks; bypass global slot; M1 receipt issuance; arbitrary table DML |
| M1 verification issuer | Existing bounded signed-receipt gateway only | M2 paid grant, task admission and provider checkpoint |

Use distinct NOLOGIN group roles and separate LOGIN credentials with no owner/superuser/`BYPASSRLS`/`CREATEROLE`/`CREATE` privilege. Do not let the web read credential inherit admission or checkpoint roles, and do not place those credentials in client code. Revoke `PUBLIC` schema `CREATE`, M2 table DML, and function `EXECUTE`; review default privileges and any old `GRANT ... ON ALL TABLES`. Explicitly grant only the intended safe view/query and gateway `EXECUTE` rights. Audit `current_user`, role membership, object owner, `has_table_privilege`, `has_function_privilege`, schema ACLs and actual negative writes with restricted connections. An owner/admin remains outside this threat model.

If `SECURITY DEFINER` gateways are later needed, create them in a trusted schema owned by the migration owner; set a fixed `search_path` such as `pg_catalog, pg_temp`, qualify all application objects and enum/helper references, disallow caller-controlled SQL identifiers, and revoke default `PUBLIC EXECUTE` in the same migration transaction before granting named roles. Neither a gateway argument like `operatorId` nor `SET ROLE` is authentication. The gateway should receive only server-authenticated, exact binding values and check them against a durable trusted decision. Never make a generic JSON-to-row insertion function for confirmation or submission.

### Narrow gateway transaction contracts (design, not SQL functions)

1. **Prepare/confirm authority boundary:** prepare is unpaid and side-effect-free with respect to jobs. A future trusted service verifies identity, scope, task-create and spend permissions separately; it stores one bounded confirmation decision with a unique server nonce and expiry. No provider call.
2. **Admit task and outbox:** explicit confirmed POST, locks Project → Movie → Studio → logical task → confirmation → dispatch. Reconstruct current M1 source and media; compare exact snapshot/script, full `ALL_CURRENT` context, Studio revision and fixed profile/quote. Reject stale/forged/replayed grant. Insert or deduplicate task, consume grant and create/update due dispatch in one transaction; compare canonical bytes on duplicate hash. A rollback must leave no consumed grant or half-created outbox. Publish a Redis `{taskId, generation}` reference only **after** commit.
3. **Claim/dispatch recovery:** bounded reconciler may republish a missing queue receipt, with task/generation/stateRevision CAS. A duplicate Redis delivery or GET cannot admit a task. Lease owner token and database-clock expiry are checked under task lock. A receipt missing after PostgreSQL commit remains recoverable; queue state is never paid authority.
4. **Checkpoint:** worker locks the same scope and task, verifies live source/script/profile/quote/current revision and grant, exact generation/stateRevision, noncancelled lease owner and the one-slot index. Insert one `StoryProviderSubmission` and transition the task in a short transaction. Only after acknowledged commit may the same process receive a one-use, nonserializable send permit. Uncertain commit acknowledgement grants **no** permit. No database transaction stays open across network I/O.
5. **Outcome:** store bounded normalized result and usage once, tied to the original checkpoint; a definitive original response may move the submission to RESOLVED, releasing the slot. Revalidate source before any candidate publication. An ambiguous outcome stays UNKNOWN, with unknown exposure. Result content never issues M1 receipts or script approval.

For every update, use a `WHERE` predicate on task ID, generation, expected stateRevision and owner (where applicable), then require exactly one affected row. A trigger requiring `stateRevision + 1` does **not** replace compare-and-swap. Gateway denial must roll back all task, grant, dispatch, checkpoint and event mutations. Keep lock order consistent; no file hash or provider request while database locks are held.

## Global unresolved slot and UNKNOWN investigation

**Recommendation:** retain the proposed single PostgreSQL-enforced slot for first live M2, subject to explicit product approval of possible indefinite head-of-line blocking. It applies only to Storyline paid submissions; legacy queues are independent. `SUBMITTED` and `UNKNOWN` occupy it. Lease expiry, timeout, process restart, cancellation request, queue redelivery, operator impatience and a local log statement cannot release it. There is no force retry, timer reset or silent multi-slot alternative.

An investigation starts from a scoped task and immutable checkpoint: task/generation, confirmation ID, request hash, server profile/version, provider correlation ID if genuinely captured, checkpoint/send timestamps, and safe transport outcome. A trusted operator with a distinct `INVESTIGATE_PAID_SUBMISSION` permission records evidence origin, retrieval time, evidence digest and a review decision in an append-only audit trail. Acceptable **definitive** evidence is the original complete response already durably captured and validated, or an authenticated provider-side lookup/support record unambiguously bound to that original request and establishing its final outcome under a verified provider contract. A billing line may establish a charge but often cannot establish response content or finality; local timeout/absence of a log proves neither no-send nor no-charge. Caller-uploaded receipts, free-text claims, screenshot-only claims and structurally plausible JSON cannot release the slot.

No second request is sent during investigation. Reconcile only the original checkpoint/generation; preserve historical result and provenance, and rerun currentness checks before any publication. Keep usage/cost `UNKNOWN` until independent provider billing/usage evidence supports another classification, even if the output outcome becomes definitive. If no trustworthy final evidence is obtainable, the correct outcome is an **indefinitely blocked Storyline paid lane** requiring operational escalation, not an automatic retry. No investigation API or manual slot-release tool is authorized now.

## Fixed profile and cost boundary

`StoryTaskProfileDefinition` is a structural shape, not a live registry. Every future paid profile must pin provider ID and exact model ID, task kind, execution class, prompt version, response schema and validator versions, policy version, profile definition hash, token ceilings, request/response byte ceilings, timeout, transport single-send policy and a versioned cost policy. Server-owned request construction must reject client model/prompt/options and clamp by both profile limits and the M2-01 structural ceilings (1 MiB request, 512 KiB response, 100,000 tokens per direction, 120-second timeout, five-minute proposal TTL). A first fake-only M2-03 fixture may use synthetic identifiers; it is **not** a selected live model.

For live quotes, pin currency and pricing source/version, input/output token unit prices, any provider overhead, exchange-rate rule if relevant, and estimation formula. Record `ESTIMATED` exposure separately from `REPORTED`/`PARTIAL`/`UNKNOWN` actual usage. The schema uses integer USD micros for stored amounts; zero is not a substitute for missing usage. The structural `maxEstimatedUsdMicros` is a ceiling on an estimate, **not** proof of a hard provider charge cap. Provider idempotency, billing finality, hard cap, remote cancellation and ambiguous-result retrieval remain `UNVERIFIED` in the pure contracts. If a hard cap is a required product promise and provider enforcement cannot be verified, paid activation remains blocked. No OpenRouter, Recap or other model is selected by this review.

## M2-03 fake-only boundary and alignment status

M2-03 may, under separate authorization, assemble the draft Prisma schema and SQL **only in a disposable database**, implement task/admission/outbox transactions with synthetic authority, publish reference-only Redis jobs, reconcile missing dispatch receipts and prove duplicate/idempotency fencing. It may use fake providers that cannot reach OpenRouter. Runtime defaults must expose no enabled paid API or Storyline worker; GET/navigation/polling must never enqueue. The live `prisma/schema.prisma`, migration history, application database, provider transport, M1 receipt activation and UI remain outside M2-03 fake-only acceptance unless separately authorized.

M2-02C aligned the review-only contracts and SQL; see [contract alignment](STORYLINE_M2_CONTRACT_ALIGNMENT.md). Pre-checkpoint redispatch keeps the same generation and consumed, unexpired grant. Expiry/exhaustion fails safely and a new generation requires a fresh consumed confirmation. An earlier cancellation request wins over terminal task publication only after the original result is stored and the submission is RESOLVED; UNKNOWN without definitive evidence remains UNKNOWN. The reviewed submission state is `RESOLVED`, and monetary storage is integer USD micros. The M1 role draft now enumerates existing tables rather than granting on all future tables; disposable tests checked both application orders and denied direct M2 DML to ordinary runtime, M1 issuer and proposed gateway roles.

These changes are review-only. They do not provide authenticated spending authority, a deployed role/gateway contract, verified provider evidence or product approval of the one-slot policy. No live M2 admission is enabled by alignment.
