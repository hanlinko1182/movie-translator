## Proven blocker and review-only files

The original six-table [M2 draft](drafts/storyline-m2-jobs.sql) ends in `ROLLBACK`, revokes `PUBLIC` table rights, and grants no admission `EXECUTE`. The proposed admission role consequently receives SQLSTATE `42501` on direct writes in either M1/M2 role-script order. The schema owner can write the tables by definition, so an application service connected as owner would bypass the intended boundary. The six-table draft also has logical `(studioId,kind,recipeHash)` uniqueness but no persisted operator/project/movie/idempotency-key binding. `StoryPaidConfirmation.authorityRef` is only a string. Pure M2 recipe and confirmation validation is structural, not authentication.

This milestone adds two **separate review-only fragments**: [ledger SQL](drafts/storyline-m2-admission-ledger.sql) and [Prisma models](drafts/storyline-m2-admission-ledger.prisma). The SQL applies after baseline + M1 + M2 only in a disposable cluster and ends in `ROLLBACK`. Neither fragment changes live Prisma schema, migrations, roles, APIs, workers, or provider configuration.

## Chosen ledger shape

| Record | Immutable binding | Database enforcement |
| --- | --- | --- |
| `StorySpendingDecision` | Subject; authority provider/version; exact project, selected movie and Studio; separate task-create and spend booleans; immutable snapshot/script IDs and hashes; task kind; recipe hash **and canonical bytes**; fixed profile/cost-policy hashes; bounded quote; expected Studio revision; generation; one submission; server nonce hash; acknowledgement, issue and expiry times; caller key | Composite Studio/source/script foreign keys, unique nonce, bounded fields, recipe projection, update/delete/truncate guards. These checks do **not** authenticate the subject/provider or prove acknowledgement. |
| `StoryAdmission` | Decision; subject and scoped idempotency key; exact task and generation; canonical recipe bytes; consumed confirmation; admission time | Unique `(subjectId,projectId,movieId,idempotencyKey)`, unique `(taskId,generation)`, unique decision and confirmation, composite foreign keys, byte-for-byte decision/task recipe comparison, consumed/unexpired confirmation comparison, append-only guards. |

The `(taskId,generation)` key allows a separately authorized later terminal generation while preventing two admissions for the same generation. An identical retry of a scoped key must return the existing admission and task **without** consuming another decision. If the same key carries different canonical recipe bytes, the future gateway must return an idempotency conflict. The unique index serializes concurrent inserts; the gateway must compare bytes after a unique conflict rather than infer identity from a hash. A new key for an already admitted same-generation recipe must not consume a second grant. None of those successful-admission behaviors is claimed as tested yet, because no gateway can safely execute them.

The decision and admission rows are historical. Neither is updated to "repair" a stale source, expired quote, revoked operator permission, or ambiguous provider submission. An expired decision is not extended in place. `StoryPaidConfirmation` remains the M2 generation-bound grant, and a future gateway must bind its `authorityRef` to an already authenticated decision ID; matching text alone is insufficient.

## Trust and gateway contract — design only

The current trusted-local application has no real authenticated spending operator. M1 `VERIFY_SOURCE` and `REVOKE_VERIFICATION` authority does not grant Storyline task creation or spending. Normal runtime must deny decision issuance and admission by default. A future **server-only** adapter must establish authenticated subject, project/movie scope, task-create permission and separate permission to spend for the exact recipe and quote, then record explicit acknowledgement. Synthetic adapter decisions may exist only inside isolated tests; neither JSON, an `operatorId` argument, a local audit label, nor a database row shape is an authority credential.

The proposed non-executable interfaces are:

1. **Issue decision:** trusted adapter reauthenticates, checks selected movie and both permissions, captures exact server-owned recipe/profile/quote, nonce and short expiry, and calls a narrow decision-issuer gateway. The issuer must be distinct from ordinary runtime, M1 verification issuer and checkpoint worker. A review of how the adapter proves its decision to PostgreSQL is required before any `EXECUTE` grant.
2. **Admit:** after explicit confirmed POST, the admission writer locks `Project → Movie → StorylineStudio → StoryTask (if present) → decision → confirmation → dispatch` in a fixed order. It compares current authoritative M1 source/media and Studio revision, exact script/profile/cost policy, decision identity, key, canonical bytes, quote and expiry. The insert or duplicate lookup, one-use confirmation consumption, task, `StoryAdmission`, due dispatch and event commit atomically. Every update uses expected generation and `stateRevision` compare-and-swap. A failed transaction leaves no partial admission or consumed confirmation. Redis publication happens only after acknowledged commit.
3. **Read/dispatch/checkpoint:** ordinary runtime gets a bounded scoped read interface only; GET never admits or publishes. Admission can neither create a provider checkpoint nor execute a worker gateway. The later checkpoint worker requires a separate fenced function and credential. `SUBMITTED`/`UNKNOWN` continue occupying the existing global unresolved slot; neither time nor reconciliation resets them.

SQL cannot hash an external source-media file or authenticate a browser session. The future service must use the M1 authoritative source integrity path and recapture around the documented lock boundary. The gateway must verify the bound database facts and refuse stale inputs, rather than treat a client-supplied currentness hash as proof.

If `SECURITY DEFINER` functions are approved later, they must be owned by a non-login migration owner in a trusted schema, use a fixed `search_path` (`pg_catalog, pg_temp`) with fully qualified application objects, take no caller-controlled SQL identifiers or arbitrary JSON-to-row payload, revoke default `PUBLIC EXECUTE` in the same migration transaction, and grant only exact function signatures to the intended role. Default privileges, owner membership and both M1/M2 script orders must be audited before deployment.

The [gateway draft](drafts/storyline-m2-disposable-admission-gateway.sql) is review-only, ends with `ROLLBACK`, names its functions `story_m2_test_*`, and must never be installed by application bootstrap. Its authority table contains synthetic fixtures, not authenticated operators.

### Authority and privilege boundary

The disposable test administrator alone seeds `StorySyntheticAuthority` with an exact subject, project/movie/Studio, immutable source IDs and hashes, task kind, canonical recipe bytes and `story-task-recipe-v1` hash, fixed profile/cost hashes, quote, revision, idempotency key, acknowledgement, and separate create/spend booleans. The issuer and admission functions derive this mapping from PostgreSQL `session_user`; neither accepts an operator label, `authorityRef`, JSON decision, recipe, scope, or spending flag from the caller. This proves restricted login binding only inside the newly owned test cluster. It does **not** prove that a web user is authenticated or permitted to spend. An authority adapter for live deployment remains undefined.

The future **server-owned authority adapter contract** must return a verified principal plus two independent decisions: `canCreateTask(principal, projectId, movieId, taskKind)` and `canSpendExactRecipe(principal, recipeHash, canonicalRecipeBytes, profileHash, costPolicyHash, quoteCeiling)`. An explicit confirmation must bind that same principal, selected scope, exact recipe and quote, a server-issued decision ID/nonce, a scoped idempotency key, one allowed submission and a short expiry. The admission service must consume only a decision established through that trusted adapter and database issuer identity. An HTTP body, local audit label, environment flag, SQL row shape or purported `authorityRef` cannot implement any of these checks. The disposable synthetic mapping emulates the adapter's already-verified output; no adapter is registered in the application or exposed through production bootstrap.

The test creates distinct NOLOGIN schema owner, synthetic issuer, admission writer, checkpoint worker and existing runtime identities. Paid-table ownership moves to the NOLOGIN owner in the isolated cluster. The issuer receives `EXECUTE` on only the synthetic issuance function; admission receives `EXECUTE` on only the synthetic admission function. `PUBLIC`, ordinary runtime, M1 verification issuer and checkpoint worker receive neither admission function nor generic paid-table DML. Admission receives no provider-checkpoint or M1 receipt-issuance permission. The functions use a fixed `pg_catalog, public, pg_temp` search path and fully qualify their own table references. `public` is included because inherited M1/M2 trigger functions contain unqualified references; the M1 role script revokes `CREATE ON SCHEMA public FROM PUBLIC`. Before any deployment, all installed trigger functions and every remaining role with `CREATE` on `public` require a separate search-path review. No application credential may be the schema owner.

### Admission transaction and measured behavior

The issuer locks `Project → Movie → Studio`, checks selected snapshot and revision, then writes a bounded single-use, expiring decision with a generated ID and nonce. The admission function locks `Project → Movie → Studio → existing Task → decision`, compares exact decision/synthetic authority fields and canonical recipe bytes, requires the fixed hash of those bytes, checks generation 0 and task revision 0, then atomically inserts the task, prepared and consumed confirmation, dispatch, event and admission. The Studio lock serializes identical submissions; the scoped idempotency unique key is a second database fence. A duplicate of the same decision/key/recipe returns the existing task without a second confirmation. A changed recipe under the same key fails. A forced late event-insert failure rolls back the new task, confirmation consumption and dispatch, leaving the previous task untouched.

The disposable test runs the gateway after baseline/M1/M2/ledger drafts in **both** M1-first and M2-first role-script orders. Separate restricted PostgreSQL connections prove true concurrent duplicate calls converge on one task. Tests also reject forged and expired decision IDs, changed operator and project/movie/Studio bindings, stale CAS tokens, mismatched recipe hash, direct table mutation, cross-role gateway calls and admission-created provider checkpoints. Existing M2 regression tests separately retain `UNKNOWN` and global unresolved-slot constraints. All fixture projects, movies, snapshots, media identities and principals are synthetic; no application `DATABASE_URL`, Redis, provider transport or real media is used.

### Boundaries for M2-03

The draft only admits a first-generation `ANALYZE_EVIDENCE` fixture recipe. It does not implement authorized terminal retry, decision revocation after issuance, runtime status reads, outbox reconciliation, source-file checksum verification, script-currentness reinspection, price enforcement, provider submission, checkpoint fencing or billing guarantees. The synthetic mapping is deliberately mutable by the isolated test administrator and is unsuitable for production. The next fake-only milestone may build a server-owned test adapter and durable outbox behavior against newly owned disposable PostgreSQL using these contracts, while keeping application admission disabled. A live gateway requires separately reviewed authentication, exact spending authorization, currentness checks around the lock, credential/role provisioning, audited trigger search paths and a deployment migration. The existing M1 verification issuer must remain separate.

## M2-03C — fenced validation and restricted delivery/read extension

The [new review-only extension](drafts/storyline-m2-transactional-gateway.sql) replaces admission's direct EXECUTE on the M2-03B insert function with `story_m2_test_open_fence` and `story_m2_test_finalize`. The original function is still owner-only and unchanged, so its independent M2-03B regression suite remains intact. The [implementation review](STORYLINE_M2_ADMISSION_IMPLEMENTATION.md#m2-03c--transaction-outbox-and-safe-read-proof) documents the transaction, privilege and test boundaries.

The test-only server closure owns an ephemeral HMAC key and creates no exported signer/validation-result API. PostgreSQL stores the key privately, while the admission role may obtain only a random challenge bound to its current backend/xid/login and exact immutable recipe/source/script/scope. The closure inspects media outside the bounded write transaction, then recaptures actual Chinese/ALL_CURRENT/QC/evidence inside that same locked transaction, validates the immutable snapshot/script and complete recipe/profile, and authenticates the challenge only after success. SQL verifies that MAC, transaction binding, age, decision expiry and CAS before atomic admission. Missing key, made-up proof, autocommit gaps, proof reuse across transactions and wrong scope cannot finalize. Media descriptor checks before signing and before completion can still abort the whole transaction.

This authenticator proves trusted server validation, **not human authentication or source verification**. The synthetic spending identity remains the original private login mapping; it cannot be supplied in an HTTP/JSON body. No SOURCE_VERIFIED receipt, real operator decision, paid provider permit or production key configuration is created. The private PostgreSQL `pgcrypto` extension is a disposable prerequisite for the HMAC proof; no application dependency is added. Any future operational signer/key-management choice requires separate review.

`storyline_outbox` can execute only bounded claim, delivery-result and explicit missing-receipt operations. The original consumed grant, cancellation/checkpoint/state, generation/revision and database-clock owner lease are checked before every write. A three-attempt test ceiling, same-generation pre-checkpoint recovery and deterministic reference-only fake receipts prevent unbounded resend. `SUBMITTED`/`UNKNOWN` are excluded by the SQL predicate shared by the entry points. A queue receipt cannot create a checkpoint, grant or task.

`storyline_m2_reader` is a new independent NOLOGIN group with a restricted test login, schema USAGE and only scoped status EXECUTE. It has no source-table rights or paid-table SELECT/DML. The function has deterministic keyset pagination, bounds 1–50, allowlisted fields/errors and truthful candidate/usage classifications. It performs no locks, writes, reconciliation or fake sends and runs inside a database READ ONLY transaction. Existing M1 runtime permissions are unchanged and are not mislabeled as a globally read-only role.

All sensitive new functions are NOLOGIN-owner SECURITY DEFINER with fixed search paths and same-transaction PUBLIC/named-role revocations. Fully qualified new references, blocked schema CREATE, absent disposable default ACLs and real negative login tests protect both role-script orders. The M1 issuer and checkpoint identities have no new spending/outbox/read gateway grants. Existing source-table SELECT for the trusted admission connection is intentionally broad enough for the current M1 Prisma reconstruction and is not a multi-user authorization claim.

**Historical M2-03C finding, resolved by M2-03D:** the M1 persister retained `candidate-*` IDs while M2 rejected them. M2-03C therefore used a separately labeled synthetic snapshot to finish its bounded protocol proof and blocked application integration. M2-03D removes that success workaround and tests the actual producer ID through database-backed eligibility; immutable history is not renamed. No application migration, Redis integration, full admission service or M2-04 worker is authorized by these proofs.
